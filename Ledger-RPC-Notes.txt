The balance math

ReverseMemoTransactionPostingServiceImpl:467-468 — the mirror image of memo posting:

long newCurrentBalance = memoEntry.getCurrentBalance();                              // unchanged
long newOpenToBuy      = memoEntry.getOpenToBuyBalance() + memoEntry.getTransactionAmount();  // restored

Memo posting did OTB − amount; reversal does OTB + amount. curr_bal never moved in either direction, because no money ever changed hands.

Crucially, the operands come from the memo journal snapshot, not from the request or a fresh tranche read — the memo row recorded the OTB at hold time, so the reversal restores to exactly that.

Worked example

Hold of 300 on T1 (curr_bal 1000, open_to_buy was 1000 → 700 after the hold).

Clear for the full 300:
curr_bal:     1000 → 700     (money actually leaves)
open_to_buy:   700 → 700     (unchanged — hold consumed exactly)
igl_memo_journal   row DELETED
igl_posting_journal  DEBIT T1 300 + netted sweep leg

Clear for 250 (merchant charged less):
delta = 300 − 250 = +50
curr_bal:     1000 → 750
open_to_buy:   700 → 750     (unused 50 released)

Clear for 350 (tip added), forcePost = false:
delta = 300 − 350 = −50
computedOpenToBuy = 700 − 50 = 650  ≥ 0 → allowed
curr_bal:     1000 → 650
open_to_buy:   700 → 650
Had the tranche only had open_to_buy = 30, computedOpenToBuy = −20 → INSUFFICIENT_BALANCE, unless forcePost diverts to the overdraft/reserved-purse rules.

Two things to note

1. Partial clearance deletes the whole memo. deleteAllById removes every memo row for the linked transaction regardless of how much was actually cleared. So clearing 250 against a 300 hold releases the leftover 50 to open_to_buy and destroys the hold — there's no residual reservation. That's the usual card-network model (one auth, one clearing), but it means you cannot clear a hold twice, and a second clearance attempt fails at step 4 with LEDGER_INVALID_LINKED_TRANSACTION_ID. That doubles as the idempotency guard.

2. The force-post validation only covers debits. validateForcePostTranche (:580) opens with if (tranche.getAuthorizedAmount() > 0) — so a zero or negative authorized amount skips the reserved-purse and overdraft checks entirely, even under forcePost. The balance math at :689 also skips its computedOpenToBuy < 0 guard whenever forcePost is true. Combined, a forcePost clearance with a non-positive amount passes through with no balance validation at all. Probably fine — a credit-direction clearance can't overdraw — but it's an asymmetry worth confirming against the intended semantics, since the equivalent non-force path does still run validateTrancheBalance.

The balance math

calculateUpdatedRevJournalBalance:540-541 — addition where direct posting subtracts:

long newCurrentBalance = trancheDTO.getCurrentBalance() + tranche.getAuthorizedAmount();
long newOpenToBuy      = trancheDTO.getOpenToBuy()      + tranche.getAuthorizedAmount();

There is no balance check — no validateTrancheBalance, no overdraft or reserved-purse logic, and forcePost / reservedPurseEnabled are never consulted. Correct: crediting an account can't overdraw it. This is the only posting type in the family without those guards.

Operands come from a fresh fetchTrancheDetails read, not from a memo snapshot — there's no memo involved.

reversalFlow = true — how the direction flips

All three journal builders are the same helpers used by direct posting, but with the last argument true (:481, :492, :502):

if (!reversalFlow) journalCode = net >= 0 ? CREDIT : DEBIT;
else               journalCode = net >= 0 ? DEBIT  : CREDIT;

So for a positive refund amount the sweep leg becomes DEBIT (settlement party owes it back) and the tranche legs become CREDIT. Same Math.abs on the amount, same netting. And because createConsolidatedSweepUnsettledTransaction shares the identical logic, the igl_unsttld_txn row mirrors the sweep leg — one row, swp_acct_id = settlementAccId, DEBIT.

The optional clearUnsettledTransaction block (:257-268) settles a previously-recorded obligation as part of the same transaction — that's how an unsettled amount from a direct posting gets closed out when the funds actually arrive.






Create Single Journal Entry RPC FLow:


What it does

Writes exactly one row to igl_posting_journal and nothing else. No balance changes, no double entry, no sweep leg, no memo, no unsettled row. It's the escape hatch for recording a one-sided journal line against the sweep account.

This is the odd one out of everything we've covered — every other flow in this service maintains balanced pairs and mutates tranche balances. This one is a pure insert.

Delete Unsettled Transactions RPC FLow:


What it does

Marks an outstanding obligation as settled, and books the offsetting journal line. Two steps, atomically:

1. Soft-delete the igl_unsttld_txn row(s) — is_soft_del = 1

So "delete" here means settle: the amount is no longer owed, and the ledger records the closing entry.
